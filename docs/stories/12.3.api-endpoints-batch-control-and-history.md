# Story 12.3: API endpoints for batch control and history

## Status

Done

## Story

**As an** administrator,  
**I want** REST API endpoints to start and stop download batches, get real-time status, and list batch history with detail,  
**so that** the UI can control the download pipeline and display progress and history.

## Acceptance Criteria

1. POST endpoint to start a new batch: accepts base_folder_path, max_size_bytes (default 200GB), optional book_ids or "all".
2. POST endpoint to cancel a running batch.
3. GET endpoint to fetch current batch status: phase, book index, part index, total size, elapsed time, storage used / limit.
4. Status updates are available via SSE, WebSockets, or polling (e.g. every 1–2 seconds) so UI stays current.
5. GET endpoint to list all batches in reverse chronological order: id, base_folder_path, status, books_downloaded, total_size_bytes, duration, started_at, completed_at.
6. GET endpoint for batch detail: full list of books (title, author, folder path, size, duration, status), errors if any.

## Dev Notes

### Context

Epic 12 MP3 bulk download. Story 12.2 implements the pipeline; this story exposes it via REST API for the UI ([Source: docs/feature-requests/mp3-bulk-download-admin.md]).

### API design

- Follow existing books-admin-app patterns: Express routes under `books-admin-app/src/routes/`
- Add new route module for downloads (e.g. `downloads.js` or `download-routes.js`)
- Use same API prefix as existing: `/api/v1/` ([Source: docs/architecture/books-admin-app-architecture.md])

### Real-time options

- SSE: simpler, one-way; good for progress stream
- WebSockets: bidirectional; more complex
- Polling: GET status every 1–2s; simplest; ensure endpoint is fast
- Feature spec says: "SSE, WebSockets, or frequent polling" ([Source: docs/feature-requests/mp3-bulk-download-admin.md])

### File locations

- `books-admin-app/src/routes/downloads.js` (or equivalent)
- Mount in `books-admin-app/src/server.js`

### Compatibility

- No changes to existing API endpoints. Additive only.

### Testing

- Integration tests: start batch, poll status, cancel; verify list and detail return correct data.

### Code Quality Assessment

Implementation follows books-admin-app patterns. Download runner owns DB lifecycle (opens from dbPath, closes when pipeline completes), avoiding use-after-close. Routes use dbRegistry.getActivePath() for DB access and pass dbPath to runner. Folder validation, book_ids resolution (array or "all"), and error responses are consistent.

### Refactoring Performed

- **File**: `books-admin-app/tests/downloads-api.test.js`
  - **Change**: Fixed flaky "returns 409 when a batch is already running" test. The test relied on the previous test's batch still running, but pipeline completes quickly (failed downloads), so the 409 test often ran after the batch had finished and got 202 instead.
  - **Why**: Test was non-deterministic; failed in CI/sandbox when network fails fast.
  - **How**: Added `waitForIdle()` helper that polls status until no batch is running (max 5s). Call it before the 409 test, then fire two POST /start requests simultaneously; one gets 202, one gets 409.
